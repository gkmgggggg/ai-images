# ADR-0010 前端视觉系统：暗色沉浸风格、语义化设计令牌、系统字体与自己实现瀑布流

## 背景

第一期前端沿用原站的野兽派视觉，用户不满意，要重做视觉和图库布局（[规格 0002](../specs/0002-frontend-redesign.md)）。这次要同时定下几件会影响所有页面的事：

- 视觉方向；
- 颜色怎么组织、怎么命名；
- 用什么字体；
- 组件库要不要加东西；
- 瀑布流怎么实现。

约束：

- 访客主要在中国大陆，页面不能依赖境外 CDN（Google Fonts 等）。
- 中文字体文件动辄几 MB，不适合作为网络字体加载。
- 列表每页 24 条，只返回摘要和 480 px 缩略图（N01）；320 px 宽起可用，弹窗要有焦点陷阱（N06）。
- 现有技术栈：Tailwind CSS 4，按 shadcn 写法用 `cva` 手写组件，弹窗用 Radix Dialog（[ADR-0003](0003-vite-spa-without-ssr.md)、[ADR-0007](0007-frontend-toolchain-versions.md)）。

## 决定

1. **视觉方向是「暗色沉浸」**：
   - 默认深色，页面以图片为主。卡片间距 6 px，卡片上的文字在悬停时才出现。
   - 强调色只有一种：钨丝灯琥珀（深色 `#f3b64a`，浅色 `#8f5a06`）。
   - 浅色主题保留，作为可选项。
   - 选定依据是 2026-09-29 的四方向 HTML 设计稿（[`specs/assets/0002/mockup.html`](../specs/assets/0002/mockup.html)）。
2. **颜色只通过语义化令牌取用**：
   - [`index.css`](../../frontend/src/index.css) 在 `:root` 和 `.dark` 上定义同一组 CSS 变量：`--bg`、`--surface`、`--surface-2`、`--fg`、`--muted`、`--faint`、`--border`、`--accent`、`--accent-fg`、`--mark`、`--header-bg`、`--overlay`。取值见规格 0002。
   - Tailwind 的 `@theme inline` 把它们暴露成 `bg-bg`、`bg-surface`、`bg-surface-2`、`text-fg`、`text-muted`、`text-faint`、`border-border`、`bg-accent`、`text-accent-fg` 等类名。
   - 组件里不写颜色值。只有两处例外，并且都集中定义：状态色（已发布、草稿、已隐藏、错误）和 JSON 着色。
   - 令牌名描述用途，不描述颜色（不叫 `--amber`）。这样以后换风格只需要改 `index.css`。
3. **只用系统字体**，不加载网络字体：
   - 正文：Avenir Next，中文依次退到苹方、冬青黑体、微软雅黑。
   - 小号标签：Avenir Next Condensed，退到 Arial Narrow。
   - Windows 上字形会不同，这一点可以接受。
4. **组件体系不变，新增一个依赖**：继续用 `cva` 加 Radix。
   - 新增 `@radix-ui/react-popover`，用于桌面端筛选面板，它自带定位、焦点管理、Esc 关闭和点击外部关闭。
   - 手机端的底部抽屉复用现有的 Radix Dialog。
5. **瀑布流自己实现**：
   - 纯函数 `computeMasonryLayout` 根据缩略图宽高算出每张卡片的位置：每张放进当前最短的一列，高宽比限制在 0.5–2。
   - 再配一个很小的窗口化 hook，只渲染视口附近的卡片。
   - 移除 `@tanstack/react-virtual`。

## 备选方案

**视觉方向**（四个方向都在设计稿里做了深浅两套、桌面和手机两种视口，用来对比）

| 方案 | 优点 | 缺点 | 为什么没选 |
| --- | --- | --- | --- |
| 极简画廊「白墙」 | 最克制，文字在图片下方常显，信息完整 | 辨识度低，和很多图库站很像 | 用户选了暗色沉浸 |
| 编辑杂志风「图录」 | 辨识度最高：宋体加 Didot，还有刊头 | 依赖宋体和 Didot，Windows 上还原度差；卡片文字多，密度低 | 同上 |
| 柔和现代「柔光」 | 最稳妥，组件现成 | 个性最弱 | 同上 |

**瀑布流实现**

| 方案 | 优点 | 缺点 | 为什么没选 |
| --- | --- | --- | --- |
| CSS `columns` | 零 JS | 按列从上往下排，阅读顺序被打乱；追加一页，所有卡片都会重新分列 | 违反 AC-2（已有卡片位置不变） |
| CSS Grid `masonry` | 原生支持 | 规范还在调整，各浏览器的实现进度不一，不能默认依赖 | 兼容性不够 |
| `@tanstack/react-virtual` 的 `lanes` | 已经是依赖 | 列的分配依赖估算高度和实测高度，图片加载后可能跳动；最短列放置不是它保证的行为 | 我们提前知道每张卡片的准确高度，用不上它的测量机制 |
| masonic、react-masonry-css 等库 | 开箱即用 | 多一个依赖；前者按测量排版，后者就是 CSS 分列 | 自己实现不到 150 行，而且可以做单元测试 |

**字体**

| 方案 | 优点 | 缺点 | 为什么没选 |
| --- | --- | --- | --- |
| 自托管拉丁网络字体（比如 Inter Tight 子集） | 各平台一致 | 多一次请求，有字体闪烁；中文部分仍然要退回系统字体，中西文混排风格不统一 | 收益小，以后需要时再单独评估 |

## 后果

- **好处**：
  - 换风格或调整颜色只需要改 `index.css` 这一个文件。
  - 瀑布流的布局可以单元测试；图片加载前就能占好准确位置，不会跳动。
  - 少了一个依赖（`@tanstack/react-virtual`），多了一个同体系的依赖（Radix Popover）。
- **代价与风险**：
  - 自己实现的窗口化要自己处理滚动监听、尺寸变化和背景路由下的滚动恢复，需要 e2e 覆盖。
  - 暗色为默认主题后，浅色主题容易被忽视。规格 0002 用令牌对比度单元测试（AC-16）兜底，e2e 截图也同时覆盖深浅两套。
  - 系统字体意味着 Windows 上的观感和设计稿有差异。
- **需要跟进**：
  - 规格 0002 批准时，本 ADR 同时改为 `accepted`；实现完成后，在 [前端架构](../architecture/frontend.md)「样式与组件」一节链接到这里。
  - 如果以后要重做品牌（Logo、favicon），另写规格。
